## 0. 总览

### 0.1 一句话架构
**一个常驻的"世界进程"（单写者）按北京时间每分钟推进世界，把状态快照和事件写入 PostgreSQL，并通过 WebSocket 向所有旁观者广播；前端（网站 / 小程序）只负责把服务端给的状态"演"出来。**

```
                         ┌──────────────── 中国大陆云（单地域）────────────────┐
旁观者浏览器 ──HTTPS──▶ CDN ──▶ 静态资源（HTML/JS/glTF/KTX2）                  │
     │                                                                        │
     ├──HTTPS GET /api/snapshot（CDN 缓存 5s）──▶ API 网关（Node）             │
     └──WSS /ws/world ───────────────────────────▶ 广播服务（Node, ws）        │
                                                      ▲  Redis Pub/Sub（可选）│
                                                      │                        │
                                           ┌──────────┴──────────┐             │
                                           │  世界进程 world-sim │ 单写者      │
                                           │  每分钟 tick        │             │
                                           └──────────┬──────────┘             │
                                  消费干预队列 ▲       │ 写快照/事件/比赛         │
                                              │       ▼                        │
管理员浏览器 ─HTTPS─▶ admin 子域 ─▶ 后台 API ─┴──▶ PostgreSQL ◀── 每日备份 OSS/COS │
                                                      ▲                        │
                                文案润色 worker ──────┘（国内已备案大模型）      │
                         └────────────────────────────────────────────────────┘
```

### 0.2 关键决策摘要
| 主题 | 决策 | 一句话理由 |
|---|---|---|
| 语言 | Node.js 22 LTS + TypeScript，前后端共享引擎包 | 样板已用 JS 写了引擎，改写成本最低；一套规则代码，前端预览/后台预测/服务端模拟共用 |
| 模拟 | 单个常驻世界进程，每分钟 tick，种子派生随机数 | 单写者无并发冲突；确定性 → 可补算、可回放、可审计 |
| 持久化 | 每分钟快照 + 追加写事件日志（PostgreSQL） | 崩溃恢复简单，历史可查，干预可追溯 |
| 同步 | WebSocket 广播 + HTTP 快照，失败回退 15s 轮询 | 小程序与网页通用；所有人看同一个世界 |
| 文案 | 模板为主，大模型只润色剧情/重大/赛后长文 | 稳定、可控、成本低；合规要求用国内已备案模型 |
| 3D | 正式版 Blender 低多边形 + glTF；样板为程序化几何 | 风格可控，包体可控，手机可降级 |
| 部署 | 阿里云或腾讯云单地域 + CDN + ICP/公安备案 | 面向大陆访问的必要条件 |

## 1. 服务端常驻模拟

### 1.1 世界时钟
- 世界时间 = 北京时间（`Asia/Shanghai`，无夏令时），1:1。
- **分钟序号** `m = floor((unixMs - EPOCH) / 60000)`，`EPOCH` 为世界开张时刻。所有状态都按"第 m 分钟"组织。
- tick 调度：世界进程用 `setTimeout` 对齐到每分钟第 0 秒（加 200ms 余量），不依赖 `setInterval` 累积误差；每次 tick 前比较"应处理到的分钟"和"已处理到的分钟"，落后则循环补算（见 1.4）。
- 一个 tick 的预算：6–12 人，事件候选约 230 条 × 人数，预编译谓词后 **< 5ms**；比赛分钟 < 2ms。CPU 不是瓶颈。

### 1.2 确定性随机数
```ts
// 每个 tick、每个用途都派生独立随机流，互不干扰
function rngFor(worldSeed: string, minute: number, stream: string): Rng {
  return sfc32(hash128(`${worldSeed}|${minute}|${stream}`)); // stream 如 "schedule:施颠" / "event-pick" / "match:2026W43"
}
```
- 同一 (种子, 分钟, 状态) → 同一结果，保证：补算与在线运行结果一致；回放可重现；比赛事先锁定后结果无法被影响。
- **内容版本也是输入**：事件库/规则热更新会改变后续结果，因此每个快照记录 `contentVersion`，回放时加载对应版本。
- 样板 `src/engine/rng.js` 已采用同样的思路（按日期+成员种子决定日程，拖动时间滑杆画面一致）。

### 1.3 状态模型与 tick 流程
```ts
interface WorldState {
  minute: number; contentVersion: string;
  members: Record<MemberId, {
    abilities: {操作,意识,对线,发育,团队,英雄池};          // 0–100，浮点
    personality: {嘴硬,心态,胜负心,逆风意志,创新欲,话痨,摸鱼倾向,甩锅倾向};
    status: {体力,心情,专注,手感,饥饿};
    activity: Activity;          // 单排/组排/双排/排队/摸鱼:xxx/社交/午饭/午睡/离开/比赛
    location: AnchorId;          // 工位/茶水区/沙发/白板/门口/不在场
    game?: {startedMin, side:'ahead'|'behind'|'even', result?}; // 当前对局
    counters: {winStreak, loseStreak, 被单杀累计, 发明流胜场, ...};
    rank: {tier, division, mmr};
    adjustTargets: AdjustTarget[]; // 后台"目标值+过渡天数"
  }>;
  relations: Record<`${A}>${B}`, number>;   // 单向关系值 0–100
  flags: Flag[];                 // {key, owner?, expiresMin}
  cooldowns: Record<`${eventId}|${memberId}`, number>; // 到期分钟
  chainBoosts: Record<eventId, number>;     // 当日加权百分比，24:00 清零
  quotas: QuotaBuckets;          // 见 3.5
  textRotation: Record<eventId, {variant:number, usedMin:number}[]>;
  milestonesClosed: string[];    // 一次性里程碑
  calendar: {nextMatch, cupBracket, holidays};
  env: {天气, 停电?, 断网?, 版本号};
}
```
每分钟：
1. `applyInterventions(queue.due(m))` —— 消费到期的后台干预（第 7 章）。
2. `updateSchedules()` —— 到岗/离岗/午饭/午睡/加班的日程推进（每人每天早上 00:00 用当天种子生成日程骨架）。
3. `updateStatuses()` —— 体力、饥饿、专注随时间变化；对局按局时长结算胜负，产生 `win/lose/behind/ahead` 等瞬时上下文。
4. `chooseBehaviors()` —— 对每个在场者按状态算行为（练习/摸鱼/社交/生活需求）。
5. `generateEvents()` —— 事件引擎（第 3 章），产生 0–N 条事件，应用效果。
6. `matchTick()` —— 比赛进行中则推进一分钟（第 4 章）。
7. `growth()` —— 有效练习累计经验（第 4.4 节）。
8. 持久化：同一事务写 `world_snapshots`（本分钟）+ `events`（本分钟新增）。
9. 发布：`{type:'tick', ...}` 增量 + 新事件到广播频道。

### 1.4 断电/重启后的状态恢复
- **启动流程**：读取最新快照 `S(m0)` → 计算当前分钟 `m_now` → 若 `m_now - m0 ≤ 1440`，从 `m0+1` 逐分钟**补算**到 `m_now`，补算产生的事件以**原分钟时间戳**写库（与一直在线时的结果相同），补算期间不广播逐条事件，补完广播一次全量快照；补算 1440 分钟约 1–3 秒。
- **超过 24 小时**：不补算（避免一口气生成几百条"过去发生的事"且关系/成长跳变）。改为把世界时间跳到当前，并插入一条自然解释事件（"办公室装修，放假两天"/"网络升级，全员调休"），由内容库里的 `L_停摆解释` 模板生成；跳过的周赛记为"赛事方延期"。干预日志同时记录一条系统条目。
- **写入原子性**：快照与当分钟事件同一事务提交；tick 幂等（`UNIQUE(world_id, minute)`），重复执行不会重复写事件。
- **快照体积**：12 人状态约 8–15 KB（jsonb 压缩后约 3–5 KB），每分钟一份，每天 1440 份 ≈ 7 MB。保留策略：最近 7 天保留每分钟；更早只保留每小时整点（回放到分钟时用整点快照 + 确定性重算）。
- **进程托管**：PM2（或 systemd）`restart: always`；`/healthz` 返回最后 tick 分钟，若落后 > 3 分钟告警（云监控 + 企业微信/钉钉机器人）。
- **主备（可选，M6 再做）**：PostgreSQL advisory lock 作为"世界锁"，只有持锁进程能 tick；备机轮询抢锁，主机挂掉 30 秒内接管，由于确定性补算，切换无缝。

## 2. 前后端实时同步

### 2.1 决策：WebSocket 单向广播 + HTTP 快照 + 轮询兜底
- **WebSocket**（`wss://api.xxx.cn/ws/world`）：服务端→客户端单向广播，客户端不发业务消息（只有心跳）。一个世界一个频道。
- **HTTP 快照**：`GET /api/snapshot` 返回当前完整状态 + 最近 50 条事件；CDN 缓存 5 秒（所有人看到同一份，回源压力恒定）。用于首屏和断线重连对齐。
- **兜底**：WebSocket 连续 3 次连接失败（公司网络代理、某些运营商）→ 改为每 15 秒 `GET /api/delta?since=<seq>` 轮询，后台每 5 分钟再尝试升级回 WebSocket。
- **为什么不用 SSE**：微信小程序没有 `EventSource`，只能用 `wx.connectSocket`；为了网页和小程序共用一套服务端协议，统一用 WebSocket。为什么不纯轮询：比赛直播需要 15–30 秒内的及时性，且推送对服务端更省（无需对每个轮询请求查库）。

### 2.2 消息格式
所有消息带全局递增 `seq`，客户端发现跳号即调用 `/api/delta?since=` 补齐。
```jsonc
// 每分钟一条状态增量（只发变化字段，平均 0.5–1.5 KB）
{"type":"tick","seq":184213,"minute":"2026-10-21T10:42+08:00",
 "members":{"施颠":{"activity":"单排","location":"desk1","pose":"sit_play","status":{"心情":72}},
            "当邓":{"activity":"摸鱼:刷手机","pose":"phone"}},
 "env":{"lights":"day"}}

// 事件（与事件板一一对应）
{"type":"event","seq":184214,"id":"ev_01JB...","minute":"2026-10-21T10:42+08:00",
 "eventKey":"U_发明流新出装","level":"有趣","category":"成长",
 "text":"施颠出了一套\"全暴击石头人\"，自称版本答案。",
 "participants":{"主角":"施颠"},"causeId":"ev_01JA...","followUps":["R_当邓批施颠出装"],
 "actions":[{"who":"施颠","pose":"stand_chat","bubble":"版本答案！","durationSec":40}]}

// 比赛直播（比赛期间每 15–30 秒一条）
{"type":"match","seq":184300,"matchId":"m_2026W43","gameMin":12,"phase":"对线",
 "goldDiff":-1300,"kills":[3,5],"text":"上路批菊被单杀一次，地鼠下路稳住了。","highlight":false}

// 心跳与版本
{"type":"hello","seq":184213,"serverTime":"...","contentVersion":"0.1.3","clientMin":"1.2.0"}
```
注意：**天意事件在消息中没有任何区分字段**（`eventKey` 与自然事件共用模板池；`intervention_id` 只存在后台库中，不进入公开表的公开视图）。

### 2.3 消息量与容量估算
- 平时：每分钟 1 条 tick + 约 0.1–0.3 条事件（每工作日 40–80 条），每连接 ≈ **1.5 KB/分钟**。
- 比赛：额外每 15–30 秒 1 条直播，比赛 40 分钟内 ≈ 120 条。
- 容量：单台 2C4G 的 Node `ws` 广播实例可稳定承载约 1–2 万连接（消息很小、频率很低）；1 万在线 × 1.5 KB/分钟 ≈ 250 KB/s 出口。超出时水平扩容广播实例，世界进程通过 Redis Pub/Sub 扇出。
- 客户端**只做插值与动画**：收到 `pose/location` 后自己寻路走过去、播放对应动画；不做任何模拟或随机，确保所有旁观者看到的"发生了什么"一致（走路的具体轨迹允许各端略有差异）。

### 2.4 历史接口
- `GET /api/events?before=<seq>&limit=50&level=` 事件板翻页；
- `GET /api/events/:id` 事件详情（参与者、前因后果、定格画面所需的当时状态快照）；
- `GET /api/members/:id` 个人卡片（能力、性格展示值、今日战绩、近 7 天曲线）；
- `GET /api/matches/:id` 赛后完整直播稿。
全部为只读、可 CDN 缓存（10–60 秒）。

## 3. 事件引擎

### 3.1 条件 DSL → 编译成谓词函数
`events.json` 中的条件是字符串（如 `act=单排`、`专注<30`、`time=09:00-11:00`、`flag=G_单排连胜三把`、`成员=当邓`、`rand<0.08`、`days_to_match<=2`、`关系>=60`）。**启动和热更新时一次性编译**：
```ts
type Ctx = { world: WorldState; slots: Record<string, MemberId>; minute: number; rng: Rng; tmp: TickContext };
type Pred = (c: Ctx) => boolean;

const GRAMMAR: [RegExp, (m: RegExpMatchArray) => Pred][] = [
  [/^time=(\d\d:\d\d)-(\d\d:\d\d)$/, ([, a, b]) => c => inTimeRange(c.minute, a, b)],
  [/^成员=(.+)$/,               ([, who]) => c => c.slots.主角 === who || Object.values(c.slots).includes(who)],
  [/^act=(.+)$/,                ([, act]) => c => actMatches(c.world.members[c.slots.主角].activity, act)], // 对局 = 单排|双排|组排|比赛
  [/^flag=(.+)$/,               ([, f]) => c => hasFlag(c.world, f, c.slots)],
  [/^rand<([\d.]+)$/,           ([, p]) => c => c.rng() < +p],
  [/^(win|lose|ahead|behind)$/, ([, k]) => c => c.tmp.gameContext(c.slots.主角) === k],
  [/^(days_to_match|hours_to_match|game_min|win_streak|lose_streak|在场|team_mood)(<=|>=|<|>|=)(\d+)$/, numericGlobal],
  [/^(旁人)?(\S+?)(<=|>=|<|>|=)([\d.]+)$/, attrCompare],   // 属性比较：主角或"旁人"
  [/^(\S+)在场$/,               ([, who]) => c => present(c.world, who)],
  [/^admin$/,                   () => c => c.tmp.fromIntervention === true],
];
function compile(cond: string, eventId: string): Pred {
  for (const [re, make] of GRAMMAR) { const m = cond.match(re); if (m) return make(m); }
  throw new UnknownConditionError(eventId, cond);   // 不静默通过
}
```
- **未知条件报警而不是静默通过**：内容 CI（`pnpm content:check`）编译全部事件，有未知条件直接失败；运行时热更新若遇到未知条件，该事件被禁用并在后台"内容健康"页报警。样板里对未知条件采取"30% 概率通过"的粗略处理，这在正式版中**必须**改掉。
- 目前 events.json 里有约 30 种非标准条件（`施颠首发`、`近10局KDA方差`、`任一能力跨越10的倍数`、`7天能力增长`、`生日当天`、`季节` 等），需要在内容 v0.2 统一为标准形式，例如 `首发=施颠`、`stat:kda_var_10<=…`、`milestone:ability_cross_10`。
- **效果**同样编译：`{attr, delta, target}` → `(ctx) => applyDelta(...)`；`A>B` 单向关系、`A<>B` 双向；`chainNext` → 当日加权；少数 `raw` 效果（`甩锅禁令@摸鱼者>持有者:1440`、`英雄池权重调整@全员`）改写为结构化 `{"type":"flag","key":"甩锅禁令","from":"摸鱼者","to":"持有者","minutes":1440}`。

### 3.2 权重公式
对每个候选（事件 e，槽位分配 s）：
```
weight(e,s) = BASE[e.level]                 // 日常 1.0 / 有趣 0.35 / 剧情 0.06 / 重大 0.01（按每人每分钟校准）
            × timeMod(e, minute)            // 时段修饰：午饭 生活×3 对局×0.3；13–15 点 睡×2.5；赛前 摸鱼×0.6 监督×1.5…
            × stateMod(e, s)                // 状态修饰：体力<30 摸鱼×2.5；手感>80 超神×3…
            × personaMod(e, s)              // 性格放大器：施颠 发明流×2.5、当邓 逆风投降×3…
            × (1 + chainBoost[e.id] / 100)  // 连锁加权（当日）
            × densityMod(minute)            // 事件密度（赛前 +30%，天意"事件密度"效果）
```
每分钟：先用"本分钟是否出事件"的泊松化概率（目标：工作日日常 30–60、有趣 8–15、剧情 1–3）决定发生次数 0–2，再按权重轮盘抽取。参数用**离线批量模拟**校准：`pnpm sim:calibrate --days 60` 跑 60 个虚拟工作日，输出每级每日条数分布、每人出镜率、每条事件命中率（找出永远不触发的"死事件"），作为内容 CI 报告。

### 3.3 组合规则需要结构化
现有 `tools/rules.json` 是**自然语言条目**，引擎无法直接执行。正式版改写为结构化规则（与自然语言并存，自然语言作为注释）：

```json
    {"when":"体力<30","match":{"category":"摸鱼"},"mul":2.5},
    {"when":"饥饿>70","match":{"tags":["外卖","零食","拼单"]},"mul":3}
  ],
  "timeMods": [
    {"time":"11:30-13:00","match":{"category":"生活"},"mul":3},
    {"time":"11:30-13:00","match":{"category":"对局"},"mul":0.3},
    {"when":"days_to_match<=2","match":{"category":"摸鱼"},"mul":0.6}
  ],
  "quotas": [
    {"scope":"member","window":"30m","level":"有趣","sameCategory":true,"max":2},
    {"scope":"member","window":"day","level":"剧情","max":2},
    {"scope":"world","window":"day","level":"剧情","min":1,"max":3},
    {"scope":"world","window":"week","level":"重大","max":2,"exclude":{"category":"比赛"}}
  ],
  "mutex": [{"group":"停电","events":["T_突然停电","T_停电"],"window":"1440m"}]
}
```
为此 `events_src.txt` 需要给事件加 `tags` 字段（如 `发明流`、`红温`、`甩锅`、`投降`），由 `gen.py` 输出。
附注：主代理已修复 `tools/gen.py` 按 `/` 切分文案变体时误切 `0/7/2` 这类战绩和 `{领先/落后}` 占位的问题，现在 227 条事件均为 2 条完整变体。

### 3.4 槽位分配（多人事件）
- 第一槽位（主角/发起者/摸鱼者…）= 当前被评估的成员；其余槽位从**在场者**中抽取，按规则 4 用关系值加权（≥70 优先包庇/双排，≤30 优先冷战/阴阳）。
- 专属槽（`施颠`、`当邓`…）锁定本人，本人不在场则事件不可用。
- `全员` = 在场者全体（≥ 事件所需人数，如五黑需 ≥5）。
- 同一事件内一人只占一个槽；`对手` 由比赛模块填充。

### 3.5 冷却、配额、去重、连锁
| 机制 | 实现 |
|---|---|
| 冷却 | `cooldowns["eventId|memberId"] = minute + cooldownMinutes`，对所有参与者生效；`0` 表示由流程控制 |
| 配额桶 | 每条 quota 规则一个滑动窗口计数器（30 分钟窗口用环形数组，日/周用自然日/自然周计数），选中前检查、选中后计数 |
| 文案轮换 | 记录每条事件每个变体的最近使用分钟，7 天内用过的变体不再选；全部用过则降级为日常灰字（按规则 5）。正式版需每事件 ≥4 个变体，否则 7 天内高频事件很快降级 |
| 去重 | 同一分钟同一参与者最多 1 条事件；同义互斥组共享窗口 |
| 连锁加权 | 事件触发后 `chainBoosts[next] += pct`，每天 00:00 清零；同一链同一参与者 3 天内不重复开启（比赛链除外） |
| 多步链 | `chains.json` 中每条链运行时生成"链实例"`{chainId, step, participants, startedMin}`，下一步事件的槽位继承上一步参与者，分支按 `if`（概率或条件）判定 |
| 一次性里程碑 | 触发后写入 `milestonesClosed`，永久不再进入候选；同时写入成员主页的"成长时间线" |
| flags | `flag=G_xxx` 由事件触发自动置位（默认当日有效）；状态型 flag（`比赛中`、`睡觉中`、`摸鱼中`）由模拟器根据 activity 实时计算，不存储 |

### 3.6 引擎的可测试性
- 纯函数：`step(state, minute, content, interventions) → {state', events[]}`，无 IO。
- 单元测试覆盖每种条件/效果语法；快照测试：固定种子跑 5 天，事件序列哈希不变（防止无意改动结果）。
- 后台"未来 1 小时可能发生"预测 = 在副本状态上用**不同的**预测种子做 200 次蒙特卡洛，统计频率，不影响真实世界。

## 4. 比赛模拟与成长系统

### 4.1 赛程（样板暂定，见待确认问题）
- **周赛**：每周五 15:00 在办公室打，BO1，约 30–40 分钟。
- **杯赛**：每月第一周抽签；在每月最后一个周五替代周赛，单败淘汰，样板中简化为单场。
- 对手为虚拟队伍（10–16 支），每队有名字、风格（速推/野核/后期/针对上路/运营）、五个位置的虚拟能力值，赛季内缓慢成长。

### 4.2 赛前锁定
- 比赛开始前 60 分钟（`T-60`）：世界进程把**首发名单、双方面板（能力×当日状态快照）、比赛种子** `matchSeed = hash(worldSeed, matchId)` 写入 `matches` 表，状态 `locked`；之后整个比赛只依赖这份存档，**管理员无法事后影响**。
- 同一时刻起，后台对**参赛成员**的状态调整与事件投放被**服务端拒绝**（API 层检查 + 世界进程消费队列时二次检查），直到比赛结束；后台页面显示倒计时和锁标识。
- 替补：按规则"近 7 天对应位置能力 + 心情"计算，差距 < 5 触发 `C_替补争夺` 链。

### 4.3 比赛过程（逐分钟）
```
队伍实力 S = Σ_位置 w_pos × 能力_pos(操作,意识,对线,发育,团队)    // 上0.18 野0.22 中0.22 AD0.22 辅0.16
           × 状态因子(平均 心情/手感/体力，0.85–1.10)
           × 配合因子(1 + 0.004×(团队均值-50) + 0.002×(吊龙团队-50)) // 吊龙指挥加成
阶段：BP(0) → 对线(1–14) → 小龙/先锋(8–20) → 中期团战(15–28) → 大龙/转折(25–35) → 结局
每分钟：goldDiff += k_phase × (S_我 - S_敌)/10 + N(0, σ_phase) + 位置对位修正
        (对线期：批菊/弟必对线弱 → 上/中路对位修正为负；弟必发育高 → 30 分钟后修正转正)
关键节点：每个团战/资源点按 sigmoid(goldDiff/2000 + 团队差) 判胜负 → 产生击杀与直播文案
逆风判定：goldDiff < -3000 时，每 5 分钟用 逆风意志+心态 判定"崩盘"或"稳住"
特殊事件：施颠首发且 rand<0.05 → C_发明流奇袭比赛（大幅加 S）；弟必首发 & 逆风 & 发育>=70 → C_弟必比赛翻盘 判定
          当邓逆风意志<55 → C_赛中投降争议；>=55 → C_当邓比赛不投了（一次性转变后首场）
结局：推塔进度 ≥ 阈值 或 35 分钟后每分钟按 goldDiff 判定水晶
```
- 直播稿：每阶段 2–4 条，转折点 1–2 条高亮，结局 1 条重大；全部来自 `C_` 模板 + 比赛专用短句模板（"第 {分钟} 分钟，{位置}…"），比赛结束后可选大模型生成一篇 300 字赛后综述（第 5 章）。
- 赛后：写 `matches.result`、更新虚拟对手战绩、触发 `C_赛后庆功`/`C_赛后复盘吵架`/`C_批菊比赛嘴硬采访`，成员获得比赛经验（倍率 ×2）。

### 4.4 成长系统
- **有效练习**：单排、双排、组排、复盘、比赛、补刀练习；摸鱼/社交/午睡时 0 经验。
- **经验 → 能力**（每局结算）：
  ```
  Δ能力 = baseXP(活动) × 方向偏向[成员][属性] × 倍率 × 递减(当前值)
  倍率   = (0.5 + 专注/100) × (0.7 + 手感/200) × (体力<30 ? 0.6 : 1) × (早到独练 ? 1.2 : 1)
  递减   = ((100 - 当前值) / 100)^1.5
  ```
  量级目标：认真的一天 +0.3～0.8（单项），一个月主方向能力 +5～10，一年左右主方向接近 75–85。
- **进化方向**：每人一张偏向表（如弟必 发育×1.6、对线×0.5；施颠 英雄池×1.8、操作×0.6），**是概率偏向不是锁死**：每局随机挑一项属性获得"顿悟"加成时，按偏向表加权抽取。突破阈值（如当邓逆风意志 ≥60）触发一次性里程碑事件。
- **被打爆也成长**：事件效果中的 `对线+0.3` 等直接作用于能力，并扣心情。
- **段位**：每位成员有隐藏分 MMR（类 Elo）：单排结果按 `期望胜率 = 1/(1+10^((对手MMR-我MMR)/400))` 更新，对手 MMR 按段位附近随机；胜负本身由"个人实力 vs 段位基准 + 随机"判定。段位由 MMR 区间映射，**每周最多升/降一个小段**（周日 24:00 结算），晋升触发 `rank_up` 事件。
- **性格**：只由重大事件和里程碑修改（如 `U_当邓不投了` 逆风意志 +x），以及后台"目标值+过渡天数"。
- **后台"目标值 + 过渡天数"**：存为 `adjustTargets: {attr, from, to, startMin, endMin}`；每天 00:00 按线性/缓动插值把差额拆成每日小增量，并在当天由模拟器挑一条**合理解释事件**（如"复盘开窍""喝了杯咖啡"）挂载上去；过渡期间若自然成长已超过目标，则提前结束。

## 5. 文案生成

### 5.1 决策：模板为主，大模型只做少量润色
| 内容 | 生成方式 |
|---|---|
| 日常、有趣事件（占 95%+） | 纯模板：`texts` 变体 + 槽位替换 + 变体轮换 |
| 剧情、重大事件 | 先用模板立即发布；**异步**送大模型润色出一段 60–120 字"展开描述"，审核通过后作为详情页正文补充（事件板标题不变） |
| 赛后综述、每周周报 | 大模型生成 300–500 字长文，异步，延迟 1–5 分钟出现 |
| 后台自定义事件 | 管理员手写，可选"大模型文风检查"（只给建议，不自动改） |

**理由**：模板稳定、可控、零延迟、零成本，且能保证"旁观者看不出管理员干预"——天意事件与自然事件共享模板池；大模型适合给少量高价值内容加厚度。**任何时候都不依赖大模型才能出事件。**

### 5.2 合规与流程
- 面向中国大陆提供服务，必须使用**已完成生成式人工智能服务备案**的国内模型（如通义千问、DeepSeek、豆包等），通过其官方 API 调用；网站需在显著位置做 AI 生成内容标识（详情页"本段由 AI 辅助撰写"），符合《生成式人工智能服务管理暂行办法》和 AI 生成合成内容标识要求。
- 流程：`events.status = published(template)` → 入队 `llm_jobs` → worker 调用模型 → **内容安全审核**（云厂商文本审核 API + 本地敏感词表）→ 通过则写入 `events.long_text`，不通过或超时 3 次则保持模板文本。
- **所有文本服务端生成后入库**，旁观者读到的永远是库里的同一份；不在客户端调用模型。

### 5.3 提示词约束（示例）
```
系统：你是"峡谷办公室"事件板的文案编辑。风格：办公室群聊 + 体育解说，短、具体、有梗，不刻薄，不涉及真实个人隐私。
人设（只可使用下列信息）：施颠=发明流、心态好、爱开玩笑、全队甩锅对象、穿人字拖；当邓=嘴硬、逆风爱投；……
硬性规则：
1. 只能润色给定事实，不得新增事件、人物、比分、KDA、时间、数值；输入中的数字必须原样保留。
2. 不得出现"管理员""系统安排""天意"等字样。
3. 不得出现真实公司名、地址、政治、色情、地域/性别歧视内容。
4. 输出 60–120 字（赛后综述 300–500 字），纯文本，不用表情符号。
输入：{事件标题模板文本}{参与者}{前因事件}{效果摘要}
```
服务端对输出做校验：字数、数字集合必须是输入数字集合的子集、禁用词，不通过即丢弃。

### 5.4 成本估算
- 剧情/重大 每天约 3–5 条 + 每周 1 场比赛综述 + 1 篇周报 ≈ 每月 150 次调用；单次约 1.5k 输入 + 300 输出 token。
- 按国内主流模型公开价位（百万 token 量级为几元到十几元人民币），**每月 < 20 元**；即使扩大到所有有趣事件也在每月百元以内。成本不是约束，审核与风格一致性才是。

## 6. 数据存储

### 6.1 决策
- **PostgreSQL 16**（云数据库 RDS 高可用版）为唯一真相源：jsonb 适合世界快照，事务保证快照与事件一致。
- **Redis**（可选，在线 > 5000 或多广播实例时启用）：Pub/Sub 扇出、快照接口缓存、在线人数计数。
- 静态内容（events.json 等）既在仓库里版本化，也写入 `content_versions` 表供回放。

### 6.2 表结构（核心）
```sql
CREATE TABLE worlds (
  id            text PRIMARY KEY,           -- 'main'
  seed          text NOT NULL,
  epoch         timestamptz NOT NULL,
  content_version text NOT NULL,
  paused_until  timestamptz                  -- 暂停世界
);

CREATE TABLE world_snapshots (
  world_id  text REFERENCES worlds(id),
  minute    integer NOT NULL,                -- 分钟序号
  at        timestamptz NOT NULL,
  content_version text NOT NULL,
  state     jsonb NOT NULL,
  PRIMARY KEY (world_id, minute)
);  -- 按月分区；7 天后只保留整点

CREATE TABLE members (
  id          text PRIMARY KEY,              -- '施颠'
  display     jsonb NOT NULL,                -- 昵称、位置、外形参数、简介
  joined_at   timestamptz NOT NULL,
  active      boolean NOT NULL DEFAULT true
);

CREATE TABLE events (
  id            text PRIMARY KEY,            -- ULID
  world_id      text NOT NULL,
  seq           bigint NOT NULL,             -- 全局递增，供客户端补齐
  minute        integer NOT NULL,
  at            timestamptz NOT NULL,
  event_key     text NOT NULL,               -- 'U_发明流新出装'
  level         text NOT NULL,               -- 日常/有趣/剧情/重大
  category      text NOT NULL,
  text          text NOT NULL,
  long_text     text,                        -- 大模型润色（审核后）
  participants  jsonb NOT NULL,              -- {"主角":"施颠"}
  effects       jsonb NOT NULL,              -- 实际应用的数值变化（后台可见）
  cause_id      text REFERENCES events(id),
  chain_instance text,
  match_id      text,
  visible       boolean NOT NULL DEFAULT true,
  UNIQUE (world_id, seq)
);
CREATE INDEX ON events (world_id, at DESC);
CREATE INDEX ON events USING gin (participants);

CREATE TABLE matches (
  id          text PRIMARY KEY,              -- 'm_2026W43'
  kind        text NOT NULL,                 -- weekly/cup
  scheduled_at timestamptz NOT NULL,
  opponent_id text NOT NULL,
  status      text NOT NULL,                 -- scheduled/locked/live/finished/postponed
  seed        text,                          -- 锁定时写入
  lineup      jsonb,                         -- 首发与替补
  panel       jsonb,                         -- 锁定时双方面板
  timeline    jsonb,                         -- 逐分钟过程
  result      jsonb
);

CREATE TABLE opponents (id text PRIMARY KEY, name text, style text, roster jsonb, record jsonb);

CREATE TABLE interventions (                 -- 干预队列 + 日志（只追加）
  id          bigserial PRIMARY KEY,
  created_at  timestamptz NOT NULL DEFAULT now(),
  operator    text NOT NULL,
  kind        text NOT NULL,                 -- inject_event/start_chain/adjust_status/adjust_target/relation/leave/env/pause
  payload     jsonb NOT NULL,
  due_at      timestamptz,                   -- 立即/定时
  due_condition text,                        -- 条件触发（DSL）
  status      text NOT NULL,                 -- queued/applied/rejected/cancelled/expired
  applied_minute integer,
  disguise_event_ids text[],                 -- 前台对应的伪装事件
  reject_reason text
);
CREATE TABLE intervention_log (              -- 状态变化流水，只 INSERT
  id bigserial PRIMARY KEY, intervention_id bigint, at timestamptz DEFAULT now(),
  actor text, action text, detail jsonb
);
REVOKE UPDATE, DELETE ON intervention_log FROM app_admin;  -- 数据库层面禁止改写

CREATE TABLE content_versions (version text PRIMARY KEY, created_at timestamptz, events jsonb, rules jsonb, chains jsonb, author text);
CREATE TABLE admin_users (id serial PRIMARY KEY, username text UNIQUE, pw_hash text, totp_secret_enc bytea, role text, disabled boolean);
CREATE TABLE admin_sessions (id text PRIMARY KEY, user_id int, created_at timestamptz, expires_at timestamptz, ip inet, ua text);
CREATE TABLE llm_jobs (id bigserial PRIMARY KEY, event_id text, status text, attempts int, output text, audit jsonb);
```
- 公开 API 使用只读账号与**视图** `public_events`（不含 `effects` 中的隐藏数值、不含任何干预关联字段）。
- 体量：事件每年约 2–3 万行；快照分区后每年 < 5 GB。单实例 2C4G RDS 足够数年。

### 6.3 备份
- RDS 自带：每日全量 + binlog/WAL 7 天，支持任意时间点恢复（PITR）。
- 额外：每日 `pg_dump` 加密上传到另一地域对象存储（OSS/COS），保留 30 天日备 + 12 个月月备。
- 每季度做一次恢复演练（恢复到临时实例，世界进程补算验证）。

## 7. 管理员后台

### 7.1 访问与安全
- **独立子域名** `admin.xxx.cn`，与公开站点不同 Cookie 域；前端为独立 SPA，不打包进公开站。
- 登录：账号 + 密码（**Argon2id**，m=64MB, t=3）+ **TOTP 二次验证**（必选）；连续失败 5 次锁定 15 分钟并告警。
- 会话：服务端会话，`HttpOnly; Secure; SameSite=Strict` Cookie，空闲 2 小时过期；所有写请求校验 **CSRF token**（双提交）+ `Origin` 检查。
- 可选 **IP 白名单**（云 WAF / 安全组）；后台接口加速率限制；操作二次确认（暂停世界、批量调整）。
- 角色：`admin`（读写）、`observer`（协管，只读：总览、日志、比赛查看）。权限在 API 层按路由强制，前端隐藏只是体验。
- 审计：每次登录、每次写操作都写 `intervention_log`；数据库账号层面禁止 UPDATE/DELETE 日志。

### 7.2 干预队列：后台从不直接改世界状态
```
后台 API ──校验(权限/比赛锁/合理性)──▶ INSERT interventions(status=queued)
世界进程 tick ──取出到期项──▶ 二次校验(比赛锁/参与者在场) ──▶ 转为"伪装事件"或状态变化
                                     │                      │
                                     ├─ 失败 → status=rejected + 原因
                                     └─ 成功 → status=applied, disguise_event_ids=[...]
```
- **单写者原则**：只有世界进程改状态，后台改动也在 tick 中按确定性流程生效 → 不会和模拟冲突，回放时干预同样作为输入重放。
- 伪装：`adjust_status` 会从"解释模板池"挑选合理事件（心情+ → "喝了杯咖啡"/"收到快递"），这些模板与自然事件共用；天意事件 (`hiddenAdmin`) 发布后在公开表里与自然事件无差别。
- 合理性提示（后台前端 + API）：投放前用引擎的条件编译器在当前状态上试算，矛盾时提示（如让请假的人组排、让不在场的人出现）。
- 定时/条件干预可撤销（`queued` → `cancelled`）；已生效的不提供回滚（保持 1:1 真实感）。
- **比赛锁**：`T-60` 至比赛结束，涉及参赛成员的 `adjust_*`、`inject_event` 由 API 直接返回 423 Locked，世界进程消费时再检查一次；比赛相关表对后台只读。

### 7.3 第一版后台范围
按草案：世界总览（复用前台 3D + 状态条）、事件投放、人物状态调整、干预日志；内容管理初期直接改仓库数据文件，经 CI 校验后热更新（世界进程监听新 `content_versions` 记录，在下一个 00:00 或手动确认后切换）。

## 8. 部署方案

### 8.1 云与拓扑（面向中国大陆）
- **阿里云或腾讯云**（二选一，倾向腾讯云：后续小程序生态、云开发与 CDN 打通更顺），单地域（华北/华东）。
- 初期资源（月成本约 400–800 元）：
  | 资源 | 规格 | 用途 |
  |---|---|---|
  | 云服务器 ×1 | 2C4G | world-sim + api + admin-api（PM2 多进程） |
  | 云数据库 PostgreSQL | 1C2G 高可用 | 主数据 |
  | 对象存储 + CDN | 按量 | 静态站、glTF、KTX2、截图 |
  | 负载均衡/WAF | 可选 | HTTPS 终止、WebSocket 转发、IP 白名单 |

### 8.2 备案时间线（与开发并行，越早越好）
| 周 | 事项 |
|---|---|
| W0 | 购买域名（.cn/.com，实名认证 3–5 天）、购买云服务器（备案需要大陆服务器） |
| W1 | 在云厂商提交 **ICP 备案**（个人或企业主体；网站名称避免"游戏""直播"等敏感词，可用"××办公室日记"） |
| W2–W4 | 管局审核，通常 1–3 周（各省不同） |
| 备案通过后 30 天内 | **公安联网备案**（全国互联网安全管理服务平台），网站底部挂双备案号 |
| 视情况 | 若启用大模型生成内容并对公众提供：使用已备案模型 API，做好 AI 生成标识；如被认定为提供生成式 AI 服务，评估是否需要登记（列入待确认） |
备案完成前可用临时域名 + 海外/港区预览环境做内部测试，但**不对公众开放**。

### 8.3 微信小程序移植路径
- 模拟全在服务端 → 小程序只需替换**渲染层和 UI 层**，协议完全复用（`wx.connectSocket` + `wx.request`）。
- 渲染两条路，M6 时按真机性能二选一：
  1. **three-platformize**（Three.js 适配小程序 WebGL Canvas）：复用 `scene/` 代码与 glTF 资源，高端机体验接近网页；
  2. **降级 2.5D**：用预渲染的等距场景图（按早/中/傍晚/夜 4 张底图）+ 人物精灵图动画，兼容低端机、包体小。
- 包体：主包 ≤ 2 MB，模型/贴图走 CDN 动态加载（需配置 `downloadFile` 合法域名）。
- **类目风险**：小程序若被归为"游戏"类目，可能需要**游戏版号**；本产品无玩家操作、无付费、纯旁观，建议以"娱乐/资讯"等非游戏类目申报，并在描述中强调"互动小说/办公室日记"属性——列入待确认问题，需提前咨询微信审核。

## 9. 3D 资源方案

### 9.1 样板 vs 正式版
- **样板**：全部程序化几何（立方体/圆柱/低细分球拼搭）+ Canvas 生成木纹贴图，零外部资源，便于快速改布局与审美方向。
- **正式版**：Blender 制作低多边形模型（参考图风格：倒角小、色块+少量纹理、柔和材质），导出 **glTF 2.0**：
  - 几何压缩：**meshopt**（解码快，首选）或 Draco；
  - 贴图：**KTX2/Basis**（UASTC 法线/ETC1S 颜色），手机显存友好；
  - 静态场景**烘焙 AO + 间接光照贴图**（Blender Cycles 烘焙，lightmap 第二套 UV），实时只保留一盏太阳方向光 + 少量点光（显示器、台灯），这样日夜变化仍是实时的，而软阴影和角落暗部由烘焙提供；为夜晚再烘一套"仅室内灯"的 lightmap，按时段混合。
- **人物**：统一骨骼（约 20 根骨骼），6（→12）人共用一套动画，外形差异用体型 shape key + 配件（眼镜、人字拖、发型）区分；动画清单：坐着打游戏（含打字循环）、起身、走、站立聊天（2 种手势）、趴桌睡、拍桌红温、欢呼、躺沙发、刷手机、喝饮料。可外包或用 Mixamo 动作重定向后手修。
- 模型来源：主体自制/外包（风格统一最重要）；绿植、杂物可用 CC0 资源（Poly Haven、Kenney）再统一材质。

### 9.2 性能预算
| 项目 | 桌面 | 手机 |
|---|---|---|
| 场景三角面 | ≤ 150k | ≤ 60k（LOD1） |
| 人物三角面 | ≤ 3k/人 | ≤ 1.5k/人 |
| Draw call | ≤ 120（合并静态网格、实例化重复家具） | ≤ 60 |
| 贴图内存 | ≤ 64 MB | ≤ 24 MB |
| 实时阴影 | 太阳光 2048 PCFSoft | 关闭，用烘焙阴影 + 人物脚下圆形假阴影 |
| 动态光源 | ≤ 8 点光 | ≤ 2（其余用自发光材质） |
| 帧率 | 60 fps | 30 fps 上限 |
| 首包（压缩后） | JS ≤ 600 KB，首屏资源 ≤ 3 MB | 同左，先出 2.5D 占位图 |

### 9.3 手机端降级策略
- 启动时检测 GPU（`WEBGL_debug_renderer_info`）、`deviceMemory`、屏幕尺寸，分三档：**高**（全效果）、**中**（DPR≤1.5、关实时阴影、2 盏灯）、**低**（DPR 1、无后期、30fps、或直接 2.5D 静态图 + 人物精灵）。
- 运行时监测帧时间，连续 5 秒低于 24fps 自动降一档。
- 页面不可见（切后台）时停止渲染，只保留 WebSocket 接收；回到前台用快照对齐。
- 样板已实现：手机竖屏事件板变底部抽屉、审核工具收进浮动按钮；画质三档——桌面"高"（DPR≤2、2048 阴影、辉光后期、显示器补光）、手机"中"（DPR≤1.5、1024 阴影、无后期）、"低"（DPR 1、无阴影、无显示器补光，可用 `?q=low` 强制）；运行中 4 秒平均帧率低于 28fps 自动关闭后期并降到 DPR 1。正式版按上面的规则把手机默认档改为"关实时阴影"。

**关键风险**
1. **备案周期不可控**（1–4 周，个别省份更久）→ M0 立即启动，上线时间以备案为硬前置。
2. **事件节奏不好看**（太吵或太闷、某些人没戏份）→ M1 必须有离线校准工具与指标，而不是上线后凭感觉调。
3. **3D 美术风格与产出速度**→ 先做一个房间角落的"风格切片"验证，再铺开；动画共用骨骼控制量。
4. **内容量不足导致重复**（每事件 2 个变体，7 天轮换下高频事件很快降级）→ 上线前高频事件扩到 ≥4 变体，可用大模型批量起草 + 人工精修。
5. **小程序类目/版号**→ 在 M5 前咨询确认，必要时小程序只做"事件板 + 2.5D"轻量版。
6. **真实朋友原型的肖像与隐私**→ 上线前取得书面同意，文案避免真实身份信息。

## 11. 待产品确认的问题

样板中已按下列"暂定"实现，正式开发前需要确认：

1. **周赛与杯赛时间**：样板暂定周赛每周五 15:00 在办公室打；杯赛在每月第一周抽签、每月最后一个周五替代周赛。杯赛是单场还是多轮（多轮是否跨周）？
2. **比赛赛制**：BO1 还是 BO3？杯赛决赛是否 BO3？
3. **节假日**：法定节假日、调休是否照常放假（办公室空着）？春节等长假期间旁观者看到什么？
4. **周末**：周六日办公室是否有人（例如有人自愿加班冲分），还是完全空置？（样板：每人约 30% 概率下午来"自愿加练"。）
5. **作息细节**：早到/加班的上限时间（样板：早到者 7:35–8:20 到岗，其余人 8:40–9:04，约 12% 概率迟到；加班最晚约 21:45；周赛前一天全员留到 19:20 之后）；夜里是否完全无人（样板：无人，但没关的显示器保持暗淡屏保）。
6. **其余 6 名成员**：加入方式（一次性加入 / 剧情化"入职"逐个加入）、时间点；办公室是否扩建（第二排工位、新房间），以及 12 人后周赛首发与替补规则。
7. **数值展示**：旁观者能否看到具体能力数值、段位、隐藏分，还是只看到条形和文字描述？
8. **事件板历史**：公开保留多久（全部 / 最近 30 天 / 只保留剧情与重大）？是否提供"按人物筛选""只看高光"？
9. **旁观人数**：顶部"在线旁观人数"是真实统计还是氛围数字？（样板为占位。）真实统计需要 WebSocket 连接计数。
10. **大模型**：是否启用润色？启用的话选哪家已备案模型、是否接受 1–5 分钟的润色延迟和 AI 标识？
11. **小程序类目**：以何种类目申报（建议非游戏类），是否需要先做咨询？
12. **肖像与隐私**：真实朋友原型的昵称、外形、性格公开展示的书面授权；是否允许本人要求修改/下线角色。
13. **音效与配音**：是否需要环境音（键盘声、空调、雨声）、事件提示音、比赛解说配音？默认静音还是开启？
14. **天意事件的边界**：管理员是否可以投放"生病""请假"这类影响个人的事件，是否需要本人同意？
15. **世界暂停**：停机超过 24 小时时的解释文案（"装修放假"等）由谁审定？是否需要提前预告？
16. **对手队伍**：虚拟对手的名字与风格由谁撰写，是否可以引用真实战队梗（存在版权/名誉风险）？
17. **段位规则**：每周最多升降一个小段是否合适？是否设置赛季重置？
18. **品牌与域名**：网站正式名称（样板暂用"峡谷打工人 · 迷你世界"，战队名"峡谷打工人"）、域名、备案主体（个人/公司）。个人主体备案对网站内容有更多限制（如不能有评论互动），需与后续是否开放留言一起考虑。
19. **样板自定的数值**：草案只给了部分性格值，样板自行补了 胜负心 / 话痨 / 摸鱼倾向（施颠 40/70/65、当邓 85/60/45、地鼠 55/85/50、弟必 60/25/35、吊龙 70/65/35、批菊 65/55/55）和初始关系值（当邓→施颠 38、批菊→施颠 42 等甩锅链方向偏低），需确认。
20. **六人五位置的替补规则**：样板认为上单位是施颠与批菊之争（当邓固定打野），按"对线+操作+心情"选首发，事件"替补争夺/solo 定首发"也只在这两人之间发生。是否正确？施颠是否也可能顶替当邓打野？
21. **工位与座次**：样板为靠窗后排 吊龙/地鼠/弟必、前排 施颠/当邓/批菊，每人桌沿灯带用其代表色。座位是否有讲究（如甩锅链的人坐在一起）？
22. **虚拟对手库**：样板临时写了 6 支（夜猫子电竞、风暴速推、老干部俱乐部、网吧之王、龙坑钉子户、甜品店五连坐），按周轮换。
23. **天意事件在样板中的处理**：样板的随机模拟器不会生成 `admin` 条件的 25 条天意事件（它们只能由后台投放），因此样板里看不到停电、版本更新等环境事件。是否希望在没有管理员操作时，世界也会以很低概率自然发生其中一部分（如下雨、外卖迟到）？
