# 美术与 3D：现有技术路线摸底 v1

> 摸底时间：2026-10-23 · 基线 `main @ 784f77c`（v0.4.0-pre / M4）
> 方式：只读调研 + 三套实现分别构建、headless 实测（未改任何源码）
> 目的：为「美术设计 / 游戏内 3D 模型」的下一步研究划出边界、接口和预算

---

## 0. 一句话结论

1. **项目里没有"美术资源"**。场景、人物、贴图、界面全部是 TypeScript 在运行时用几何体和 Canvas 画出来的；除标签页图标 `favicon.ico` 外，游戏运行时没有任何外部图片、模型、字体、音频文件。
2. **人物不是模型文件**，是「Capsule / Sphere / Lathe / Cone 拼装 + 15 个程序姿态」。这也是唯一被官方明确"挂起"的美术项（`docs/RELEASE-NOTES-v0.4.0-pre.md`：「人物造型挂起。画面仍是现在的低多边形几何体」）。
3. **远端有两条未合并的美术支线**，把人物换成两种互斥的方案：`art/figurine-lowpoly`（代码生成的切面手办）和 `cursor/gltf-figurine-template-911b`（glTF 手办模板 + 运行时换色）。两条都还没合进 `main`，而且都改写了同一份《人物造型定稿》文档、结论相反。
4. **当前性能瓶颈是场景的 mesh / draw call，不是三角形数**：网吧场景一帧约 2.6k draw call、1.4k 个 mesh、37 万三角；六名选手只占三角 18%，但和路人、外卖员一起，人物类 mesh 约占全场景一半。
5. **头身比是造型差距的核心**（按代码尺寸估算）：锁定图要的是「1:2.2～2.5 的大头手办」，主线现在是 **1:5.4**，切面版 **1:2.7–2.9**，glTF 版 **1:3.0–3.3**。任何"3D 模型研究"都绕不开这个数。

## 2. 资源管线：从源码到双击可玩

```
src/**/*.ts ──tsc 检查──> vite 打包 ──vite-plugin-singlefile──> dist/index.html
                                                              （JS/CSS 全内联，无外链）
运行时 Canvas 2D ──> THREE.CanvasTexture ──> 材质（屏幕、地板、招牌、白板、窗外）
```

- **没有资源目录**：没有 `assets/`、没有 `.glb/.gltf`、没有 `.png` 贴图、没有字体文件、没有音频。
- **文本全部是代码里的中文字符串**，界面用系统字体栈（`PingFang SC` 等），因此离线可玩，但字形随系统变化。
- **贴图全部运行时生成**：`scene/textures.ts` 里 13 个生成器——显示器画面（256×160）、地板、墙面、地毯、瓷砖、隔板、白板（可实时重绘）、窗外城市（可随昼夜重绘）、海报、画框、霓虹招牌、价目牌、底座刻字。
- **离线与平台约束**（设计文档第 2 章）：不直接调用 Node/Electron；存档走 `platform` 接口层；M6 再用 Electron 套壳出 .exe。
- **对 3D 模型研究的含义**：一旦引入 glTF/贴图等外部资产，就必须回答"怎么塞进单文件"——base64 内联约 **+33%** 体积；若放 `public/` 则不再是单文件。

## 3. 渲染舞台（`scene/stage.ts`）

| 项 | 现状 |
|---|---|
| 渲染器 | `WebGLRenderer`，antialias，`PCFSoftShadowMap`，`ACESFilmicToneMapping`，sRGB 输出 |
| 环境光 | `PMREMGenerator` + `RoomEnvironment`，`environmentIntensity = 0.35`（夜里降到约 0.09） |
| 相机 | **PerspectiveCamera fov 26°**（近似等距），默认距离 33（横屏）/ 46（方形）/ 更远（竖屏，按宽高比最多约 80），OrbitControls 限定极角 0.55–1.15、方位角 π/4 ± 0.75 |
| 后期 | 高画质才开 `EffectComposer`：RenderPass → **UnrealBloomPass**（强度 0.4、阈值 0.82、半径 0.55）→ OutputPass |
| 标签层 | `CSS2DRenderer`（头顶名牌、对话气泡是 DOM，不是 3D 文字） |
| 拾取 | 射线检测人物身上的**隐形圆柱**（半径 0.32·g，高 1.85·s） |
| 画质档 | high：dpr≤2、2048 阴影、bloom；medium：dpr≤1.5、1024、无 bloom；low：dpr 1、无阴影 |
| 自动降档 | 4 秒内平均 <28fps → 关 composer、dpr=1 |
| 构图 | 右侧面板通过 `camera.setViewOffset` 让场景在可见区域居中 |

## 4. 场景美术（`scene/venue.ts` → `netcafe.ts` / `office.ts`）

### 4.1 装配逻辑
- 按存档的**场地等级**选场景：0 = 网吧角落（`buildNetcafe`），1–3 = 小办公室 / 电竞基地 / 豪华基地（都走 `buildOffice`，后两级只换墙色和招牌）。
- 按**已购买设施**决定渲染：饮水机、零食柜、耳机升级、冰箱、沙发、白板、公司餐补（`data/facilities.ts`）。没买的不渲染、队员也不会去用。
- 场地或设施变化 → `syncVenue()` 重建整个场景（人物保留、瞬移回位）。
- 走位靠**导航图**（`nav.ts`）与**站位表**（`spots.ts`）：门口排队、赛前会站位、饮水机/零食柜/冰箱/沙发的使用点。

### 4.2 建模方式
全部是程序几何，`office.ts` 里有一组复用函数：

| 函数 | 用途 |
|---|---|
| `box / rbox` | 墙、地台、家具（`RoundedBoxGeometry` 圆角，带几何缓存） |
| `cyl / lathe` | 杯子、花盆、奖杯、泡面桶、饮料瓶 |
| `plant` | 绿植：车削花盆 + 11 片椭圆叶（种子随机） |
| `mat(color, opts)` | 材质缓存（按颜色 + 参数 JSON 作 key） |
| `shadow / addMesh` | 统一投影/受影 |

网吧场景的实际内容：6 台战队机位（贴面桌、隔板、厚边框显示器、灰色机箱、**破皮老板椅**：露海绵、胶带、缺扶手）、3 排散客机位、网管吧台 + 货架 + 收银牌、饮水机、「小心地滑」牌 + 拖把桶、绿植、窗外城市、霓虹招牌「星空网吧」、价目表、墙上挂钟。

> 美术信息量其实很高（磨损、胶带、泡面、价目表），但**全靠代码堆**：每件家具都是独立 mesh，没有合并、没有实例化。

### 4.3 短板
- 没有 UV 规划、没有烘焙、没有 AO、没有法线；观感偏"硬"。
- 没有 LOD、没有合批、没有 instancing；`rbox` 只有几何缓存，没有材质合并。
- 户型只有一张：电竞基地 / 豪华基地 = 换墙色 + 换招牌（RELEASE-NOTES 已注明）。

## 5. 人物 3D 模型（重点）

### 5.1 结构：关节是空 Group，网格挂上去

```
root ─ body ─ hips ─┬─ spine ─┬─ neck ─ head ─┬─ 脸/眼/眉/腮红/嘴/鼻
                    │         │               ├─ hairCap / 刘海 / 发撮
                    │         │               ├─ glasses（可选）
                    │         │               └─ headset（可选，默认隐藏）
                    │         ├─ sh(L) ─ el(L) ─┬─ sleeve / upper / fore / hand / thumb
                    │         │                 └─ phone / cup（挂右肘）
                    │         └─ sh(R) ─ el(R) ─ …
                    ├─ hp(L) ─ kn(L) ─ foot(L) ─ shoe 或 flipflop
                    └─ hp(R) ─ kn(R) ─ foot(R) ─ …
```

- **关节只做旋转插值**，层级就是骨架。没有 `SkinnedMesh`、没有 `Bone`、没有动画片段。
- 关键常数：`HEAD_R = 0.155`、`SEAT_H = 0.5`、`WALK_SPEED = 1.35`、腿长 `0.84·s`、躯干 `0.30·s`、点击柱 `1.85·s`、名牌高度 `2.1·s + 0.14`。
- **六人参数**（`roster.ts` 的 `look`，与《人物造型定稿》一致）：

| 人 | height | girth | hairStyle | 眼镜 | 人字拖 | 衫色 |
|---|---|---|---|---|---|---|
| 阿鸡 | 1.00 | 1.10 | messy（9 撮锥体） | ✓ | ✓ | `#ff8a2b` 橙 |
| 当邓 | 0.84 | 0.86 | short | ✓ | | `#2f8a4a` 绿 |
| 狗粮 | 0.90 | 0.90 | short | ✓ | | `#4a8ad4` 蓝 |
| 弟必 | 1.15 | 0.88 | side（侧分刘海） | ✓ | | `#f2efe8` 米白 |
| 吊隆 | 1.02 | 0.98 | buzz（板寸） | | | `#1e3a6e` 深蓝 |
| 撇干 | 0.98 | 1.18 | short | | | `#c43a3a` 红 |

- 胖瘦不是等比放大：臂/腿用 `sqrt(g)` 缩半径，躯干车削轮廓单独收腰，`g > 1.15` 才加肚皮球。
- 材质全是 `MeshStandardMaterial` 纯色（皮肤 roughness 0.62、衣服 0.85、头发 0.8），胸口是金色圆片队徽，不是锁定图的白六边形星标。

### 5.2 动画：姿态表 + 角度插值

- **15 个姿态**：`stand / walk / sit_play / sit_phone / sit_relax / sit_eat / sleep_desk / slump / rage / cheer / chat / drink / watch / lie / reach`。
- 每个姿态返回各关节目标角（髋高、躯干前后倾、头三轴、肩/肘/髋/膝），`update()` 里按 `k = dt*9` 插值。走路带摆臂、抬膝、身体起伏；`rage` 会抬手拍桌（`onSlam` 触发桌子抖 + 镜头震）。
- 转身沿最短角差，`dt*8` 插值；眨眼随机 2–6 秒；睡觉时闭眼；`lie` 姿态整体绕脚底 -90° 再抬到沙发高度。
- **对模型研究的要求**：任何新模型必须继续吃这套角度（关节名一致），或者重写动画层——后者是数天级工作量。

### 5.3 道具与复用
- 手机（右手、屏幕自发光颜色随 App 变）、杯子（右手）、耳机（头上，罩色=衫色）、人字拖（阿鸡）。
- **同一套 Character 被复用**：4 名网吧路人 + 1 名网管 + 1 名外卖员（黄衣 + 保温箱）+ 6 名选手 = 场景里 12 个人物实例，约 700 个 mesh。
- 外卖员走位是"按游戏分钟贴在路径上"，不是逐帧模拟。

### 5.4 识别性
- 头顶 CSS2D 名牌（衫色圆点 + 名字 + 状态 emoji），可点击；气泡是 DOM。
- 因为相机远（距离 33、fov 26°），人物在屏幕上很小，审查报告的原话是"基本靠昵称标签认人"。**这是 3D 模型研究的第一个验收场景**。

## 6. 光照与氛围（`scene/lighting.ts`）

- 太阳按游戏内时刻算方位/高度（`clock.sunPosition`），颜色从暖白到橙；日夜三段调色板（夜 / 晨昏 / 昼）混合半球光、地面色、背景色与窗外天空。
- 阴影视图 22×22、bias -0.0004、normalBias 0.03、radius 4。
- **8 个点光源**：6 台战队显示器的补光 + 1 盏霓虹招牌灯 + 1 盏室内暖光（夜里按在场人数亮）。前向渲染下这是真实开销。
- 台灯 / 灯罩自发光、底座灯带、机箱灯、键帽辉光、显示器 emissiveMap 都是氛围来源。
- 夜景是强项：bloom 强度随夜色从 0.2 → 0.8、曝光 +25%、环境反射降到 25%、窗外灯点重绘。

## 7. 界面与视觉语言

- 深海军蓝毛玻璃（`backdrop-filter: blur(14px)`）+ 暖橙强调色（`#f0a35e`）+ 金/绿/红的状态色；圆角 14px；系统字体。
- 3D 与 DOM 混排：3D 场景铺底，名牌/气泡是 CSS2D，顶部 HUD、事件看板、人物卡、经营/赛前/直播/结算全部是 DOM 弹窗。
- 人物卡片、积分榜、直播弹幕都不依赖 3D 美术，改版成本低；**真正的美术工作量集中在场景与人物两处**。

## 9. 两条未合并的美术支线

### 9.1 `origin/art/figurine-lowpoly`（2 个提交，落后 main 4）

**做了什么**：把手办风格做成"切面块"，用 **凸包（ConvexGeometry）** 从点云生成一刀刀削出来的面；拆出 `body.ts`（比例/骨架）、`hair.ts`（发际线 + 发盖 + 发尖 + 刘海程序算法）、`pose.ts`（姿态表）、`lineup.ts`（白底六人站位，`?lineup=1`）。

| 项 | 内容 |
|---|---|
| 体型 | **统一标准体型**，`look` 里的 height/girth 被删掉；全员黑发；`FIG = 1.4`，站高约 **1.45 m**（旧版约 1.72 m） |
| 造型语言 | 大头（头身比 ~1:2.7–2.9）、切面四肢、V 领、白六边形队徽、深藏青短裤、蓝人字拖、弟必挂脖耳机 |
| 关键文件 | `scene/{body,figure,hair,pose,lineup,character}.ts`，`tests/look.test.ts` |
| 实测 | 单人 2.5k 三角 / 90 个 mesh；场景 2,948 draw call；包体略降 |
| 优点 | 零资产、单文件纯净、头身比最接近锁定图、面数降 77% |
| 风险 | **统一体型和拍板设定直接冲突**（撇干最胖 / 狗粮偏瘦 / 弟必最高全部丢失）；mesh 数上涨；所有造型迭代仍要改代码 + 重新构建 |

### 9.2 `origin/cursor/gltf-figurine-template-911b`（1 个提交，落后 main 5）

**做了什么**：用 683 行的 Node 脚本 `scripts/build-figurine.mjs` **手写 glTF 二进制**，导出 7 个 .glb（body / 4 发型 / 眼镜 / 耳机），运行时 `GLTFLoader` 加载、按材质名换色、按 `look.height` 缩放、按 `girth` 只拉 xz。

| 资产 | 三角 | 材质 | 节点 |
|---|---|---|---|
| body.glb（87.5 kB） | **1,008** | 8 个（matSkin/Shirt/Pants/Shoes/Badge/Eye/Brow/Mouth） | 48 个，含 `hips/spine/neck/head`、`armL_sh/el`、`legL_hp/kn`、`socket_hair/glasses/headset` |
| 4 种发型（5.2–11.5 kB） | 60 / 120 / 132 / 148 | matHair | 头顶挂点 |
| glasses.glb（6.7 kB） | 72 | matGlasses/matLens | |
| headset.glb（12.7 kB） | 156 | matHeadsetBand/Cup | |

| 项 | 内容 |
|---|---|
| 比例 | 模板高 1.00 m，运行时 `root.scale = height × 1.72`（实测 1.445–1.978 m）；头身比约 **1:3.0–3.3** |
| 接口 | 节点名 = 现有 Group 名，`poseTargets` 直接写欧拉角；胖瘦 `lerp(0.88, 1.22, …)` 只作用在躯干/四肢 |
| 实测 | 单人 1.3–1.5k 三角 / 35–37 mesh；包体 1,048 kB（含 models 副本共 ~1.19 MB）；离线运行零报错 |
| 优点 | 面数最低；**接得上 Blender 等 DCC 管线**；材质槽/挂点定义清晰 |
| 风险 | 破坏"单文件无外链"的干净承诺（+25%）；`public/models` 与 `src/scene/figurine` 双份资产；模板本身是脚本生成的，视觉上限仍受脚本限制；需要额外构建步骤 |

### 9.3 与主线的关系

- 两条都**没有合并**，`main` 的发布说明仍写"人物造型挂起"。
- 两者**互相排斥**：体型（统一 vs 保留）、资产（零资产 vs glTF）、比例（1.4 vs 1.72）、发色与配色（切面版改了阿鸡橙发/全黑发/全员人字拖）。
- 两条都改写了《人物造型-定稿-稿B-v1.md》：主线的版本写"**不引入 glTF**"，glTF 支线把这句话改成"**改用 glTF 手办模板**"。**这是目前最需要先拍板的一句话。**

## 10. 做 3D 模型不能破的边界

## 12. 3D 模型路线选项

| | A 程序几何精修（主线现状） | B 切面手办（figurine 支线） | C glTF 模板（gltf 支线） | **D 混合（推荐）** |
|---|---|---|---|---|
| 视觉上限 | 低（真实比例、圆管四肢） | 中高（按规格最接近锁定图） | 高（可进 DCC） | 高 |
| 迭代方式 | 改 TS 立即见效 | 改 TS 立即见效 | Blender/脚本 → 重新导出 | 角色走 DCC，场景留代码 |
| 包体 | 不变 | 略降 | **+25%** | +15–25% |
| 三角 | 11k/人 | 2.5k/人 | 1.4k/人 | ≤3k/人 |
| mesh / draw call | 58/人 | **90/人** | 37/人 | 需合并到 ≤20/人 |
| 姿态接口 | 现成 | 现成 | 现成（同名节点） | 现成或加蒙皮 |
| 风险 | 永远差一口气 | 与"胖瘦/高矮"设定冲突 | 单文件纯度、双份资产 | 需要一次资产管线决策 |

**推荐 D，落地顺序：**

1. **先定接口合同**（不改美术）：关节名、挂点（hair/glasses/headset/phone/cup/badge）、材质槽名、比例基准、坐姿髋高、名牌高度。写成 `docs/人物模型-接口合同.md`，两条支线都按它对齐。
2. **先搭校验台**：把 `?lineup=1` 白底六人站位搬进 main（纯调试视图，不引美术），所有造型对比都在同一个镜头下出图。
3. **再做一次 A/B**：同一角色（建议阿鸡）分别用切面版和 glTF 版出同角度近景，对照锁定图打分，再决定管线。
4. **场景并行做合批试点**：把网吧 6 台机位做成可复用模块 + 合并几何，目标 draw call 砍 30%，给人物腾预算。
5. **定预算再开工**：建议单人 ≤3k 三角、≤20 mesh、全场景 ≤150k 三角、draw call ≤1.8k、贴图总量 ≤4 MB。

## 13. 需要拍板的三件事

1. **要不要引入外部美术资产**（Blender / glTF）？——这一条决定 B 和 C 谁继续。（现状：主线文档写"不引入"，glTF 支线已改口。）
2. **体型是否保留个人差异**？——锁定图拍板过"撇干最胖 / 狗粮偏瘦 / 弟必最高"；切面支线为了统一标准体型把它们删了。两者不能同时成立。
3. **单文件体积上限**是多少？——840 kB 是现状，glTF 路线约 1.05 MB；如果将来要放 7 个高精度角色，需要定一个"能发给朋友"的上限。
